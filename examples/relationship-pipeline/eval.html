Evidence limitations

This public example contains fictionalized reproductions derived from observed failure modes. It is not the private production dataset, does not estimate real-world prevalence, and does not validate a model judge.

Failure taxonomy

Application-specific failures discovered from traces or deliberately induced scenarios. Synthetic provenance must be visible.

contact-tone-leakage block observed

Outgoing tone inflates relationship warmth

The model treats the user's friendly outbound language as evidence that the recipient engaged.

Expected: Classify warmth from recipient behavior only.

Impact: high · Repeated during manual testing

contact-invention block observed

Unusable text creates an invented contact

The model returns a placeholder identity when no person can be identified.

Expected: Return no contact identity when the input contains no identifiable person.

Impact: medium

premature-state-change block observed

Application is marked ready before confirmation

The workflow permits a state change on the same turn that it first presents the extracted application.

Expected: Require explicit confirmation in a later user turn before marking the application ready to log.

Impact: critical

ungrounded-analysis review observed-derived

Pipeline answer ignores supplied data

The assistant gives generic advice without using the counts and entities supplied in the product state.

Expected: Cite the relevant supplied counts and base the recommendation on them.

Impact: high
